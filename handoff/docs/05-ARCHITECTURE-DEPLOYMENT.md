# 架构、持久化与部署交接

交接包版本：V1.1.0；游戏规则版本沿用V1.0.0。日期：2026-10-21（Asia/Hong_Kong）。适用范围：Astra规划、Sol实现的文字麻将首版。游戏规则以[01-RULES.md](01-RULES.md)为准；本文件规定实现边界，不增加玩法。

## 1. 实施目标与已知边界

交付一套可在Mac运行的Web应用，2—6名玩家通过浏览器加入好友房；火山云只承担公网入口和隧道转发。一个服务实例拥有全部牌局真相，客户端负责交互和渲染。首版使用单进程Node服务与本机SQLite，不需要把牌局拆成多个微服务。

截至本包交付，仅完成方案、模板和资料核验；未访问用户Mac、云主机或域名，未声称完成实机安装、SSL签发或公网联机。缺少现场凭据不阻塞规则引擎、真实本地多人测试及部署材料交付。现场步骤见第10节。

推荐运行时为Node.js 24 LTS，实施时选该受支持分支的已修复补丁版本，将精确版本写入`.node-version`、`package.json`和交付报告。Node官方发布表在查阅日将24列为LTS；版本选择依据是受支持状态，不是追求最新主版本。[S01](09-SOURCES.md#s01)

## 2. 源码职责与模型分工

| 目录 | 所有者与职责 | 禁止越界 |
|---|---|---|
| `packages/contracts` | 共享类型、运行时输入验证、错误码；先按包内契约落地 | 不含Socket连接、数据库、React |
| `packages/engine` | Sol：纯规则、牌权、状态转换、投票与定时事件 | 不直接读网络、系统时间、环境变量 |
| `apps/server` | Sol：身份、房间队列、持久化、定时器、Socket.IO投影 | 不向浏览器发送完整内部状态 |
| `apps/web` | Astra：EnglishMahjong Three.js牌桌、DOM编辑/投票、可见状态和adapter | 不自行判胡、计票或修改权威牌局 |
| `tests` | Sol实现自动化；Astra复核场景与视觉结果 | 不用mock单页代替多人联机验收 |
| `deploy` | Sol落地可运行配置，保留环境隔离；本包给模板 | 不覆盖用户现有frp/Caddy服务 |

引擎建议导出`reduce(state, command, context)`，返回新状态、事件、定时任务意图及对当前请求的应答。`context`注入时钟、随机源、玩家认证上下文；测试使用假时钟和固定随机种子。生产洗牌种子从服务端安全随机源生成，种子与未来牌山不进入客户端投影。

不要在两个位置各维护一份规则。AI、回合超时、真人出牌都调用同一合法命令入口，不能直接改数组绕过引擎。

### 2.1 V1.1.0 新增：采用既有 Three.js 牌桌

用户选择的来源是EnglishMahjong-web，固定提交与快照见[11-ENGLISH-TABLE-ADOPTION.md](11-ENGLISH-TABLE-ADOPTION.md)。前端沿用React+TypeScript，新增/明确Three.js渲染层；不为移植桌面而换服务端或运行原站英文游戏。

技术依赖由执行者锁定精确补丁版本；上游package-lock仅是研究基线，不应把所有上游依赖整包覆盖本项目。实现时记录Three.js与类型包版本、构建输出和GPU支持。采用上游相机/材质/实例渲染时先保持其视觉，再按性能证据优化。

数据流固定为：SocketAdapter接收公共快照和本人私密快照→按版本一致性建立TableViewModel→Three.js场景与React/DOM层订阅。它们是两个显示层，不是两个游戏状态源。显示类型见[contracts/table-view.ts](../contracts/table-view.ts)。私密与公共版本暂时不匹配时保留最后一致画面并请求同步，不能把别轮/别身份手牌拼入新公共状态。

桌面默认用3D本人手牌，投影DOM命中/可访问性层向唯一SentenceRackController发动作；展开整理句子时隐藏对应3D本人手牌，用DOM呈现。手机竖屏为3D桌+DOM手牌。草稿和逗号始终只有一份；相机缩放/视口改变时同步投影命中区域，必要时冻结拾取直到坐标一致。

**逻辑运行在Mac，3D渲染运行在每个玩家自己的浏览器。**火山云只转发应用字节流，不承担远程画面渲染。客户端性能问题不能靠提高云机CPU解决；应按视口/DPR降低阴影和后处理，维持文字与交互清晰。

### 2.2 显示容量、动画与故障

- LayoutProvider从room.capacity与mySeat计算显示槽位；原四人常量及90度相机转座全部替换。服务端seatIndex不随视角变化。
- 原108牌池改成按本局总牌数及纯视觉余量构建。最大字库216张；同一物理牌在任意时刻唯一归属，ghost/候选只作视觉引用。溢出不得slice丢对象，应报开发错误并使用可恢复的显示方式。
- 其他人仅数量和无字牌背，牌墙仅剩余数；renderer不构造也不缓存对手暗牌正面。摄像机限制仅控制体验，隐私必须来自数据最小投影。
- 引擎提交和ACK优先于动画。动画队列用roundId/phaseId/controlEpoch/stateVersion及显示generation判过期；取消旧动画不能再次发游戏命令。
- WebGL context丢失是显示故障，不等于Socket离线。先保住同一身份/命令链/草稿，切同状态2D回退，恢复context后从最新一致快照重建场景。回退不成为正常设备的默认产品形态。
- 退出或重建时释放geometry/material/texture/render targets/composer，移除监听器与RAF。共享纹理使用引用计数，不能每帧或每次拖字重建。汉字纹理按字形而非tileId复用，牌实例仍按tileId区分。

逐文件实施、程序几何和字体路线以docs/11为准，实际手机/视觉/性能验收以[12-UI-ACCEPTANCE.md](12-UI-ACCEPTANCE.md)为准。上述为必须实现的要求，不是当前交接包已测得的性能结论。

## 3. 单房间串行处理与版本

每个roomId有一个串行队列。真人命令、网络断线/恢复、AI延时动作、投票截止和服务重启恢复事件全部入队。一个房间只允许一个状态变更事务进行；不同房间可以交错调度。

处理顺序固定为：

1. 识别真实玩家身份和当前控制会话；客户端提交的playerId只能作匹配，不能作为认证。
2. 对已认证主体查询`actionId`去重记录。已成功的同一动作返回原提交结果，不再次执行；旧会话不得借重试重新取得控制权。
3. 核对roomId、roundId、phaseId、controlEpoch、阶段权限和牌权；校验负载尺寸、牌ID、逗号及异议区间。
4. 在当前权威状态上运行纯引擎，检查牌数、唯一归属、合法轮次等不变量。
5. 一个SQLite事务内写事件、最新快照、去重结果，必要时写结算/胜局计数。
6. 提交成功后才替换内存状态、确认动作、向每个人发送各自投影并安排新定时器。提交失败不广播“已出牌”。

### 三个版本字段分别解决不同问题

| 字段 | 含义 | 判断方式 |
|---|---|---|
| `stateVersion` | 房间已提交状态的递增序号 | 用于快照新旧、审计和刷新；不能代替阶段权限 |
| `phaseId` | 本次行动、弃牌响应或投票阶段的唯一ID | 已离开阶段的延迟请求必须拒绝 |
| `controlEpoch` | 当前席位的控制权代数 | 恢复登录后旧浏览器、旧AI任务不得写入 |

多人可能都看着stateVersion=20同时投票。第一票令状态变成21，第二票仍然应在同一proposalId、phaseId和冻结评审集合内有效。**不能对投票、PASS/HU/EAT登记一概要求expectedStateVersion等于当前全局值。**互斥命令如弃牌则检查行动阶段、实体牌归属与是否已完成，并对冲突返回明确错误及刷新指引。最终类型字段和错误名采用[contracts/types.ts](../contracts/types.ts)。

定时器按作用范围捕获标识：阶段截止捕获`roomId + roundId + phaseId + timerId`；席位AI另带`playerId + controlEpoch`。`GRACE_END`按玩家控制代次和原缓冲截止验证，不能被普通回合phase变化取消；`RETENTION_END`按暂停实例和保留期限验证。触发时先入队，再检查仍然有效。取消定时器只是优化，正确的代次/阶段/期限验证才是正确性保障。

## 4. SQLite数据与崩溃恢复

### 最小持久化模型

| 表/集合 | 至少包含 |
|---|---|
| `rooms` | roomId、容量、房主、规则版本、字库版本、状态、保留截止时间 |
| `players` | playerId、roomId、seatIndex、昵称、当前controlEpoch、恢复码哈希 |
| `sessions` | 会话令牌哈希、玩家ID、有效期、是否撤销；不保存明文cookie |
| `room_snapshots` | roomId、stateVersion、schemaVersion、完整权威状态、保存时间 |
| `room_events` | roomId、序号、事件类型、内部事件数据、服务端时间 |
| `action_receipts` | 主体、roomId、actionId、结果和提交后的版本；唯一索引防重复 |
| `round_results` | roundId唯一、胜者/流局/终止、句子快照、匿名投票汇总 |

内部快照可以包含暗牌、洗牌顺序和审计所需评审对应关系；它是服务器私有数据，不能直接序列化为客户端消息，也不能以“调试下载”公开。公共历史仅含匿名结果。会话凭据、恢复码明文和密钥不能写入事件。

每次影响牌局的有效动作都存快照；私人排句草稿可去抖保存，离开页面前主动提交，恢复时按当前牌权修剪。客户端断网且尚未确认的草稿不能假称已同步；UI标识“已保存/本机草稿”。

使用SQLite WAL与短事务，数据库放在Mac本地磁盘。WAL依赖同机共享内存，不应把活跃数据库直接置于NAS、网络文件系统或同步盘。[S02](09-SOURCES.md#s02) 实施时记录实际SQLite引擎版本，选已包含WAL-reset修复的版本；官方文档列出3.51.3及后续版本，也列出特定旧分支回补。[S03](09-SOURCES.md#s03)

建议配置`foreign_keys=ON`、`journal_mode=WAL`、`synchronous=FULL`及合理`busy_timeout`，并用单写入连接/队列控制事务。数据库适配器版本、实际SQLite版本、迁移编号都要进入构建信息；不假设“Node版本新，所以内嵌数据库必然符合要求”。

### 必须验证的崩溃边界

- 事务提交前崩溃：动作不生效；恢复后可合法重试。
- 提交后、ACK前崩溃：去重收据已存在；重试返回原结果，不能再摸/出一张。
- 获胜结算时崩溃：`roundId`唯一约束阻止重复加胜局。
- 进程重启：进行中房间进入`PAUSED_RECOVERY`，重建期限和控制epoch；不要重放过期setTimeout。
- 重启时离线已超过24小时保留期：结束为过期，不被一次登录重新激活。

Socket.IO连接状态恢复仅能辅助临时网络断开，官方明确它可能失败；它不替应用恢复服务器崩溃后的数据库状态。[S04](09-SOURCES.md#s04)

## 5. 对外投影和实时通信

生产将静态前端、HTTP接口和Socket.IO放在同一HTTPS域名。开发使用同源代理，避免把开发跨域设置带入生产。

| 投影 | 可以包含 | 不可包含 |
|---|---|---|
| 公共房间 | 玩家昵称/座位/连接模式/牌数、弃牌、轮次、剩余牌数、公开候选句子 | 任一暗牌、未来牌山、恢复码、会话令牌 |
| 本人私密 | 公共状态＋本人手牌/草稿/可执行操作＋本人已投状态 | 他人暗牌、别人投票倾向和异议选区 |
| 结算公共 | 赞成/反对/未投总数、阈值、匿名合并异议 | 评审者ID与赞反的对应关系 |
| 服务端内部 | 完整权威状态、冻结集合、去重和审计 | 永不直接作为Socket广播负载 |

Socket.IO保证消息顺序，但默认不保证每条事件一定送达；额外交付机制要由应用实现。[S05](09-SOURCES.md#s05) 客户端重连时发送自己已确认的版本，由服务器提供最新本人快照。首版可以统一用小型完整投影，减少“遗漏一个增量后永久错位”的风险。服务器每次响应都带状态版本和服务端时间，倒计时在客户端只显示，不作裁决。

约定`/healthz`只反映进程存活，`/readyz`反映数据库可用、迁移完成且能接受新房间；不得泄露房间列表或用户数据。维护排空时ready可为503，已有房间允许收尾。前端资源采用带内容哈希文件名；规则版本不兼容时提示刷新，不能继续发旧负载。

## 6. 身份恢复与简单AI

### 真人恢复

使用服务器签发的随机会话，生产cookie设`HttpOnly`、`Secure`、`SameSite=Lax`和明确有效期；或实现等价保护。相同域名的HTTP与Socket.IO使用同一身份。HTTP写操作及Socket握手验证Origin/必要CSRF令牌，生产允许来源精确等于`PUBLIC_ORIGIN`，不使用任意来源通配符配合凭据。

恢复码使用足够长度的随机值，首次入座时只向本人显示。服务器仅存哈希，恢复请求走HTTPS请求体，不放在URL、邀请链接、WebSocket查询参数或公共消息中。用比较安全的固定时序校验策略，并对失败恢复尝试限速。恢复成功在同一房间队列内更换有效会话、增加controlEpoch、撤销旧控制会话并发送本人快照。

若选择高熵随机恢复码，可以存SHA-256/HMAC摘要；若实施时改成短人类口令，则需要慢哈希和更严格限速，不能未经决策偷偷把长恢复码换成6位房间码。

### 简单AI是确定性规则模块

输入只包含自己的可弃手牌、字库权重和公共弃牌；输出一张合法tileId。优先处理重复字、再按权重选择，平局使用已注入的随机源。AI不读他人暗牌，不读下一张牌，不吃、不申胡、不投票，不接大模型API。

15秒缓冲、800毫秒动作延时、全员离线暂停、申请人掉线撤回等规则完全采用R-040—R-048。AI延时动作与真人恢复竞争时，以房间队列中提交先后为准；已提交动作不回滚，未提交旧epoch动作无效。这是恢复原位和防双动作的核心。

## 7. 网络部署结构

| 节点 | 监听/连接 | 职责 |
|---|---|---|
| 浏览器 | 访问`https://mahjong.example.com` | 页面、HTTP动作、Socket.IO连接 |
| 火山云Caddy | 公网TCP 80/443 | HTTPS入口；转发全部应用路径到`127.0.0.1:7300` |
| 火山云专用frps | 控制TCP 7000；代理仅`127.0.0.1:7300` | 建立到Mac的隧道 |
| Mac frpc | 主动连接云控制端口7000 | 将代理流量送到本机3000 |
| Mac游戏服务 | `127.0.0.1:3000` | 页面、房间服务、SQLite |

frps的`proxyBindAddr`决定代理监听地址，`allowPorts`限制允许绑定的代理端口；对应模板把代理口锁到云回环地址及7300。[S06](09-SOURCES.md#s06) 本方案使用TCP代理运送HTTP/Socket.IO字节流，不需要再把frp传输方式改为WebSocket。Caddy反向代理原生支持WebSocket升级和双向传输。[S07](09-SOURCES.md#s07)

**模板假定使用本游戏专用frps实例。**如果用户已有消息中枢或其他frp业务，不得直接覆盖原配置。尤其`proxyBindAddr`与`allowPorts`是全局配置，修改共享实例会影响其他服务。若7000已占用，给本游戏选空闲控制端口，并同步frpc、服务配置及云安全组；7300若占用同样改动两侧。不得为了省一步而停掉现有业务。

云安全组开放80/443用于网页，frp控制端口按Mac出口网络条件限制来源；7300不开放公网，Mac的3000也不做公网映射。管理SSH沿用用户既有管理方式，不把SSH、数据库或frp管理面板添加到游戏域名。

浏览器到Caddy使用HTTPS；frpc到frps使用TLS并验证服务端证书。frp官方说明默认TLS开启加密，但默认不验证frps证书，因此模板额外给出CA、SAN域名和证书路径。[S08](09-SOURCES.md#s08) 真实证书和密钥由现场配置生成/提供，不含在交接包。Caddy公网证书与frp隧道证书是两套用途，不要把“网站锁头正常”当成隧道身份校验已完成。

## 8. 配置文件的使用边界

`deploy/`中每个`.example`都是模板。先复制为实际环境文件，替换占位域名、用户名、绝对路径、密钥和证书；再用所安装软件的原生配置验证命令检查。TOML能解析只证明语法，不能证明证书存在或云端已连通。frp支持`frpc verify -c`与`frps verify -c`预检。[S09](09-SOURCES.md#s09)

应用规则数值从`contracts/rules.defaults.json`读取并入库冻结，不用环境变量悄悄改变正在进行中的规则。`.env.example`只列运行环境、存储和传输设置。

Mac使用两个独立LaunchAgent：游戏服务与frpc。模板采用绝对程序路径，不假设Apple Silicon的`/opt/homebrew`或Intel的`/usr/local`一定存在。`launchd`不会替你读取交互shell里的nvm配置；Node用明确路径和`--env-file`加载配置。用户级Agent只在该用户登录期间运行，这一点与系统级daemon不同。[S10](09-SOURCES.md#s10)

约局时Mac接电并避免自动睡眠，屏幕可关闭。Apple提供显示器关闭时防止接电自动睡眠的选项；合盖后的具体行为需按设备环境实测，不承诺“开启一次设置便可任意合盖常开”。[S11](09-SOURCES.md#s11)

## 9. 备份、发布与回滚

生产目录建议将不可变发布物和可变数据分开，例如`releases/VERSION`、`current`、`shared/config`、`shared/data`、`shared/logs`、`shared/backups`。同一数据库只由一个游戏服务实例写入；不以启动两个进程抢3000端口的方法做滚动升级。

备份使用SQLite在线备份API或`VACUUM INTO`等支持一致快照的方式。不要在活跃WAL模式下只复制主`.sqlite`文件并当成完整备份；SQLite官方给出了在线备份方案。[S12](09-SOURCES.md#s12) Sol需实现本项目的`db:backup`命令，输出新文件并执行`integrity_check`，把结果和应用/schema版本写入备份清单。运行数据库、会话记录与恢复凭据视为私密数据，不提交git。

发布顺序：完成本地验收 → 备份并确认可恢复 → 暂停新开房并等待已有局结束，或显式安排维护暂停 → 停游戏服务 → 执行受控迁移 → 切换发布目录 → 启动并检查ready → 在真实网络开一局验证 → 恢复新开房。

正常重启应处理SIGTERM：停止接新命令、完成正在提交的事务、写当前快照、关闭数据库和连接。即使优雅关闭失败，也必须依靠已提交快照恢复，不能仅靠退出钩子临时保存全部进度。

回滚优先采用兼容迁移，恢复上一发布物即可使用当前库。若schema不兼容，必须先停服务，保留故障库，再恢复匹配备份；这可能丢失备份后的对局，只能在记录影响范围后执行，不能自动静默回滚数据。备份与回滚用沙盒数据先演练一次。

## 10. 分层上线验证与交付证据

| 层级 | 验证动作 | 合格证据 |
|---|---|---|
| A 本机 | Mac访问3000，2—6独立浏览器上下文，实际服务端 | 全人数测试、牌数一致、规则及AI恢复报告 |
| B 隧道 | 云机访问`127.0.0.1:7300/healthz`与ready | HTTP成功；7300仅回环监听 |
| C 公网 | 用手机蜂窝网络访问游戏域名 | HTTPS正常，Socket.IO建立并能共同打一局 |
| D 恢复 | 单人断网10秒、20秒；刷新；换设备恢复；服务重启 | 分别命中缓冲/AI/原位恢复/暂停恢复，牌不多不少 |
| E 隔离 | 两房间并行；查看网络消息；伪造座位/旧epoch | 不串房、不漏暗牌、不接受旧控制者动作 |
| F 运维 | 备份恢复、无损应用回滚、Mac显示器关闭 | 恢复后的数据与记录一致，在线能力按现场结果记录 |

只完成A层时，应交付“本地可运行，公网待现场配置”，并明确剩余DNS、证书、云安全组及端口映射步骤。不能把B/C层标为通过，也不要因缺云端凭据而停止本地实现。

Caddy重载可能关闭已有WebSocket连接，官方文档说明该行为及可调参数。[S07](09-SOURCES.md#s07) 游戏必须把它当作真实短暂断线测试一次；不要靠“部署时大家别刷新”掩盖恢复缺陷。

## 11. 完成定义

Sol交付真实可启动的应用、锁定依赖、迁移/备份命令、运行记录及现场部署说明；Astra交付已接真实状态的界面并复核所有人数与离线/投票状态。最终说明必须分清：自动化通过、人工实际验证、尚待现场验证。不要把本文件的部署模板或UI参考截图当成游戏已完成证据。
